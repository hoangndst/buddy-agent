## 1. The Problem

During initial live testing of `buddy-agent`, three architectural and user-experience failure modes emerged:

1. **Protocol Rigidity & Gateway Rejections**:
   `buddy-agent` was hardcoded exclusively to OpenAI's legacy `/v1/chat/completions` wire format. When connected to reasoning-capable models on Azure OpenAI or proxy gateways (such as `gpt-6-luna` or `o3-mini`), the server defaults to enabling reasoning effort. The `/v1/chat/completions` specification explicitly rejects function tool calls when reasoning is active, returning:
   ```json
   {
     "message": "Function tools with reasoning_effort are not supported for gpt-6-luna in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'.",
     "type": "invalid_request_error",
     "param": "reasoning_effort"
   }
   ```
   Without support for the newer `/v1/responses` Responses API or adaptive `reasoning_effort` sanitization, the agent cannot execute tool-assisted workflows with modern reasoning models.

2. **Accidental Conflation of Conversational Output with Thoughts**:
   In `internal/agent/engine.go`, any text generated by the model was unconditionally emitted as an `EventThought` and rendered in muted gray italics in the terminal. Casual conversational responses (e.g. "Hello, how can I help you today?") appeared as internal thinking rather than direct assistant output.

3. **Intrusive Step Noise in Interactive Chat**:
   The interactive REPL printed raw `\n[Step %d]` banners on every execution turn. For conversational interactions that do not require external tools, this debug telemetry created visual clutter and made the CLI feel like a test harness rather than an intuitive pair programmer.

---

## 2. Overview

Milestone 5 transforms `buddy-agent`'s client engine into a **dual-protocol model provider architecture** paired with a **human-centric REPL terminal interface**:

- **Dual-Protocol Engine with Diagnostic-Triggered Negotiation**:
  - Encapsulates `/v1/chat/completions` (universal for Ollama, vLLM, OpenRouter, and standard instruction models) and `/v1/responses` (OpenAI Responses API for simultaneous reasoning and tool use) behind an isolated `ModelProvider` interface in `internal/agent/provider/`.
  - Features **Diagnostic-Triggered Protocol Escalation**:
    - Local endpoints (`localhost:11434`, loopback addresses) are immediately pinned to `chat` without network probing.
    - Remote endpoints default to `/v1/chat/completions` to eliminate the 404 probing latency penalty across 90%+ of cloud gateways (OpenRouter, DeepSeek, Together, Groq, remote vLLM).
    - When a remote gateway returns the specific reasoning conflict diagnostic error on tool turns, `AutoProvider` immediately escalates to `/v1/responses` and latches `responses` for subsequent turns.
  - Implements **Adaptive Reasoning Effort**: Configurable via `BUDDY_REASONING_EFFORT` (`none`, `low`, `medium`, `high`), automatically sanitizing parameters if `/v1/responses` is unsupported by the gateway.

- **Transparent Operational Visibility & Clean REPL**:
  - Decouples internal chain-of-thought tokens (`EventReasoning`) from conversational output (`EventTextComplete`).
  - Emits conversational text cleanly in standard foreground styling upon completion, while tool invocations display formatted action summaries (`formatToolPreview`).
  - Prepares the event stream data model for Milestone 6 (SQLite trajectory store) and Milestone 9 (Bubbletea interactive TUI streaming with `EventTextDelta` and `Ctrl+O` expandable views).

## 3. Goals & Non-Goals

### In-Scope Goals
- **Zero Model Hardcoding Invariant**: The provider architecture and auto-negotiation engine must never rely on hardcoded model name lists or vendor string matching. Protocol negotiation and parameter adaptation are driven strictly by endpoint topology, runtime HTTP capability probing, and gateway diagnostic feedback. Any model identifier string (e.g., `gpt-6-luna`, `qwen2.5-coder:7b`, `deepseek-r1`, or custom fine-tunes) works without modification.
- **Pluggable `ModelProvider` Abstraction**: Create `internal/agent/provider` containing `ModelProvider`, `ChatCompletionsProvider`, `ResponsesProvider`, and `AutoProvider`.
- **Precedence Hierarchy & Configuration**:
  - `BUDDY_API_TYPE`: `auto` (default), `chat`, or `responses`.
  - `BUDDY_REASONING_EFFORT`: `none`, `low`, `medium`, `high` (default: empty / unconstrained).
- **Event Decoupling**: Separate `EventReasoning` from conversational text in `internal/agent/types.go`, retaining `EventThought` as a backward-compatible alias.
- **Enriched Event Telemetry**: Add `Timestamp`, `Duration`, `Protocol`, `Usage` (`int64` prompt, completion, reasoning), `ToolExitCode`, and `ToolCallID` to `agent.Event` to ensure forward compatibility with Milestone 6 and Milestone 9.
- **Terminal Polish**: Remove raw `[Step 1]` headers from conversational turns; pretty-print tool invocations for all native and MCP tools.
- **100% Backward Compatibility**: Zero regressions for local Ollama, vLLM, OpenRouter, standard OpenAI endpoints, and Milestone 3 Three-Partition context memory compaction.

### Out-of-Scope Non-Goals
- **Native Anthropic `/v1/messages` Wire Protocol**: Anthropic models are supported via OpenAI-compatible proxy gateways (e.g. OpenRouter). Native Anthropic SDK integration is deferred to a future dedicated provider milestone.
- **Interactive TUI Keybindings**: Full keyboard navigation, scrolling viewports, and interactive `Ctrl+O` expand/collapse toggles are reserved for Milestone 9 (Bubbletea TUI).
- **Real-Time Token-by-Token Streaming**: Milestone 5 utilizes synchronous unary provider generation. Output text is emitted via `EventTextComplete` upon turn completion; real-time incremental token streaming (`EventTextDelta`) is reserved for Milestone 9.
- **Database Schema & Trajectory Storage**: SQLite table migrations and query execution are reserved for Milestone 6 (SQLite State Persistence).

### 4.2 Pluggable `ModelProvider` Subsystem (`internal/agent/provider/`)

All LLM network interaction is encapsulated behind a clean Go interface in `internal/agent/provider/`:

```go
// ModelProvider abstracts wire protocols for the agent execution engine.
type ModelProvider interface {
    // Protocol returns the canonical wire protocol identifier ("chat" or "responses").
    Protocol() string
    // Generate executes a completion or response step with the underlying LLM service.
    Generate(ctx context.Context, req GenerateRequest) (*GenerateResponse, error)
}
```

#### Canonical Data Contracts
`GenerateRequest` bridges engine state to wire clients without circular package dependencies:

```go
type GenerateRequest struct {
    Model           string
    Messages        []openai.ChatCompletionMessageParamUnion
    Tools           []tools.Tool
    ReasoningEffort string
    MaxTokens       int
    IsLocal         bool
    LocalNumCtx     int
}

type GenerateResponse struct {
    Content          string
    ReasoningContent string
    ToolCalls        []ToolCall
    Usage            TokenUsage
    Protocol         string
}

type ToolCall struct {
    ID        string
    Name      string
    Arguments string
}

type TokenUsage struct {
    PromptTokens     int64
    CompletionTokens int64
    ReasoningTokens  int64
    TotalTokens      int64
}
```

#### Turn Commitment & History Integration Adapter
To maintain 100% backward compatibility with Milestone 3's `internal/history.Session` (which commits turns via `session.CommitSimpleAssistant(msg openai.ChatCompletionMessage)` and `session.CommitToolTurn(msg openai.ChatCompletionMessage, results []ToolResult)`), `GenerateResponse` provides a clean synthesizer helper:

```go
// ToChatMessage converts normalized GenerateResponse into an openai.ChatCompletionMessage
// for seamless commitment into history.Session without modifying the TurnBlock data model.
func (r *GenerateResponse) ToChatMessage() openai.ChatCompletionMessage {
    msg := openai.ChatCompletionMessage{
        Role:    openai.ChatCompletionMessageRoleAssistant,
        Content: r.Content,
    }
    if len(r.ToolCalls) > 0 {
        msg.ToolCalls = make([]openai.ChatCompletionMessageToolCall, len(r.ToolCalls))
        for i, tc := range r.ToolCalls {
            msg.ToolCalls[i] = openai.ChatCompletionMessageToolCall{
                ID:   tc.ID,
                Type: openai.ChatCompletionMessageToolCallTypeFunction,
                Function: openai.ChatCompletionMessageToolCallFunction{
                    Name:      tc.Name,
                    Arguments: tc.Arguments,
                },
            }
        }
    }
    return msg
}
```

#### Tier 2 Memory Compaction Adapter
`session.EnsureWatermarks` and `session.ForceCompaction` require `history.CompletionClient`:
```go
type CompletionClient interface {
    CreateChatCompletion(ctx context.Context, params openai.ChatCompletionNewParams, opts ...option.RequestOption) (*openai.ChatCompletion, error)
}
```
In `internal/agent/provider`, `CompletionClientAdapter` wraps `ModelProvider` (or direct `*openai.Client`), allowing Tier 2 distillation prompts to execute transparently across both `/v1/chat/completions` and `/v1/responses` without breaking package decoupling.

### 4.3 Provider Implementations

#### 1. `ChatCompletionsProvider` (`/v1/chat/completions`)
- Wraps `client.Chat.Completions.New(ctx, params, opts...)`.
- Maps `req.Messages` directly to `ChatCompletionNewParams`.
- Maps `req.Tools` to `[]openai.ChatCompletionToolParam` using `tools.Registry.OpenAITools()`.
- Injects local `options.num_ctx` when `req.IsLocal` is true.
- Injects `reasoning_effort` when non-empty.
- Extracts `resp.Choices[0].Message.Content`, parses tool calls, synthesizes fallback tool IDs (`fmt.Sprintf("call_%d_%d", step, idx)`) if omitted by local models, and captures `resp.Usage` as `int64`.

#### 2. `ResponsesProvider` (`/v1/responses`)
- Wraps `client.Responses.New(ctx, params, opts...)` using `github.com/openai/openai-go/responses`.
- Implements `mapMessagesToResponseInputs`:
  - `openai.ChatCompletionSystemMessageParam` -> instructions parameter or system message item.
  - `openai.ChatCompletionUserMessageParam` -> user input message item.
  - `openai.ChatCompletionAssistantMessageParam` -> assistant message item with tool calls mapped to function call items with `CallID`.
  - `openai.ChatCompletionToolMessageParam` -> `responses.ResponseInputItemFunctionCallOutputParam{CallID: toolMsg.ToolCallID, Output: toolMsg.Content}`.
- Maps `req.Tools` to `[]responses.ToolUnionParam`:
  ```go
  tool := responses.ToolParamOfFunction(t.Name(), schema, false)
  tool.OfFunction.Description = openai.String(t.Description())
  ```
- Translates `req.ReasoningEffort` to `responses.ReasoningParam{Effort: ...}`.
- Extracts conversational text via `resp.OutputText()` and separates reasoning output items.

#### 3. `AutoProvider` (Diagnostic-Triggered Escalation & Latching)
- Maintains an atomic `latch` state (`int32`: 0 = unlatched, 1 = latched chat, 2 = latched responses).
- **Topology-Aware Fast Path**: Local endpoints (`IsLocalEndpoint`) immediately pin to `ChatCompletionsProvider` with zero network probing.
- **Remote Inverted Default (Zero 404 Overhead)**:
  - Default remote protocol starts with `ChatCompletionsProvider`.
  - On conversational turns, `chat` executes cleanly with zero 404 probing overhead.
  - When tools are executed, if Azure / proxy gateway returns `CapabilityErrorReasoningConflict` (`"Function tools with reasoning_effort are not supported..."`), `AutoProvider` retries immediately via `ResponsesProvider` and atomically latches `responses`.
  - If `ResponsesProvider` returns `CapabilityErrorEndpointUnsupported` (HTTP 404 or 405), `AutoProvider` latches `chat` and retries with `reasoning_effort: "none"` as emergency fallback.
- **Operational Error Fast-Fail**: Transient errors (HTTP 401, 403, 429, 5xx, or network timeouts) fail fast immediately without retrying or mutating latch state.

### 4.4 Capability Error Classification (`internal/agent/provider/llmerr.go`)

To avoid circular package dependencies (`internal/agent <-> internal/agent/provider`), error classification is implemented entirely within `package provider`:

```go
type CapabilityErrorKind int

const (
    CapabilityErrorNone CapabilityErrorKind = iota
    CapabilityErrorEndpointUnsupported // HTTP 404/405 on /v1/responses
    CapabilityErrorReasoningConflict   // HTTP 400 function tools with reasoning_effort unsupported
    CapabilityErrorParamRejected       // HTTP 400 parameter unrecognized
)

// ParseCapabilityError analyzes API error responses to determine protocol or parameter capability issues.
func ParseCapabilityError(err error) CapabilityErrorKind
```

`internal/agent/llmerr.go` remains dedicated to `ParseContextLengthError(err)` for token ceiling compaction triggers.

### 4.5 Event Stream Decoupling & Schema Enrichment (`internal/agent/types.go`)

Resolves the gray-italic conversational text display issue while providing forward-compatible contracts for Milestone 6 (SQLite) and Milestone 9 (Bubbletea TUI):

```go
type EventType string

const (
    EventStepStart        EventType = "step_start"
    EventReasoning        EventType = "reasoning"          // Model chain-of-thought tokens
    EventThought          EventType = "reasoning"          // Deprecated alias for backward test compatibility
    EventTextDelta        EventType = "text_delta"          // Reserved for Milestone 9 streaming tokens
    EventTextComplete     EventType = "text_complete"       // Unary conversational assistant response
    EventToolCall         EventType = "tool_call"           // Tool invocation with formatted preview
    EventToolResult       EventType = "tool_result"         // Tool output observation
    EventFinished         EventType = "finished"            // Turn or task finished
    EventError            EventType = "error"
    EventCompactionStart  EventType = "compaction_start"
    EventCompactionDone   EventType = "compaction_done"
    EventMicroPruning     EventType = "micro_pruning"       // Retained from Milestone 3
    EventContextRetrying  EventType = "context_retrying"
    EventContextExhausted EventType = "context_exhausted"
)

// Event conveys rich real-time execution telemetry to listeners.
type Event struct {
    Type         EventType
    Step         int
    Timestamp    time.Time
    Duration     time.Duration
    Protocol     string           // "chat" or "responses"
    Content      string           // Text or reasoning payload
    ToolCallID   string           // Unique ID for M6 SQLite foreign keys & M9 TUI collapsing
    ToolName     string
    ToolArgs     string
    ToolResult   string
    ToolExitCode int              // 0 for success, non-zero exit status, or -1 for tool error
    Usage        TokenUsage       // int64 Prompt, completion, and reasoning token metrics
    Error        error
}
```

### 4.6 Human-Centric Terminal REPL Presentation (`internal/cmd/root.go`)

The terminal renderer in `internal/cmd/root.go` is upgraded for clear pair-programming ergonomics:

1. **Eliminating Raw Step Banners**:
   - `EventStepStart`: Does NOT print `\n[Step %d]`.
   - On tool steps, an unobtrusive step indicator is included in the tool header (`⚙ [Step 2] bash: go test ./...`).

2. **Distinct Reasoning Styling**:
   - `EventReasoning`: Styled in a dedicated thought container:
     ```text
     💭 Thinking:
        The user wants to inspect project files. I will run ls to check directory contents...
     ```

3. **Clean Conversational Output**:
   - `EventTextComplete`: Rendered directly to `f.IOStreams.Out` in primary foreground text without italics or dimmed styles.

4. **Pretty-Printed Tool Actions (`formatToolPreview`)**:
   - Implemented in `internal/cmd/root.go`:
     - `bash`: `⚙ bash: <command>`
     - `read_file`: `⚙ read_file: <path>`
     - `write_file`: `⚙ write_file: <path>`
     - `edit_file`: `⚙ edit_file: <path>`
     - `save_memory`: `⚙ save_memory: <topic>`
     - `create_skill`: `⚙ create_skill: <name>`
     - MCP tools: `⚙ <tool_name>: <primary_arg>`
     - Fallback: `fmt.Sprintf("⚙ %s(%s)", name, rawArgs)` safely used if JSON unmarshaling fails.

## 5. Alternatives Considered

### Alternative 1: Only Support `reasoning_effort: "none"` in `/v1/chat/completions`
- **Description**: Avoid building a new Responses API client by strictly injecting `reasoning_effort: "none"` on `/v1/chat/completions` whenever reasoning models call tools.
- **Why Rejected**: While this requires minimal code and resolves the Azure gateway 400 error, it completely strips reasoning models (such as o1, o3, and gpt-6-luna) of their chain-of-thought capabilities during tool use. Autonomous agent harnesses require deep reasoning to plan complex multi-step tool sequences; suppressing reasoning eliminates the model's primary architectural advantage.

### Alternative 2: Replace `/v1/chat/completions` Entirely with `/v1/responses`
- **Description**: Migrate the entire agent harness exclusively to OpenAI's new Responses API.
- **Why Rejected**: Local inference engines (Ollama, vLLM, LM Studio, llama.cpp) and multi-model gateways (OpenRouter) do not implement the proprietary /v1/responses endpoint. Hardcoding the harness to /v1/responses would break local-first, zero-cloud development and prevent using open-source models.

### Alternative 3: Static Model Name Heuristics for Protocol Selection
- **Description**: Use hardcoded model string prefixes (e.g. `if strings.HasPrefix(model, "o1") || strings.HasPrefix(model, "o3")`) to choose between `/v1/responses` and `/v1/chat/completions`.
- **Why Rejected**: Hardcoded model lists violate the Zero Model Hardcoding Invariant. Static name matching fails when users deploy custom fine-tunes, enterprise internal models (such as gpt-6-luna), or new models released after binary compilation. Runtime capability negotiation and topology probing ensure future-proof compatibility with any model string without software updates.

### Alternative 4: Deferring All UX and Terminal Formatting Polish to Milestone 9
- **Description**: Leave the terminal REPL untouched until Milestone 9 (Bubbletea TUI), focusing solely on the wire protocol in Milestone 5.
- **Why Rejected**: The current REPL contains an active presentation bug where conversational output is rendered in muted gray italics as thought blocks, and intrusive [Step 1] banners clutter simple chat turns. Addressing the event stream decoupling and terminal renderer in Milestone 5 immediately improves developer ergonomics while locking down the exact event contracts needed for Milestone 6 (SQLite) and Milestone 9 (Bubbletea).
